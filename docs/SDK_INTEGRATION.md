# Argus SDK Integration

Argus helps platforms verify that user-submitted photos were captured through an Argus-controlled in-app Android capture flow. It is designed for workflows where a fresh photo matters, such as marketplace listings, insurance claims, warranty or returns intake, rental and real-estate media, field-work audits, and other evidence-heavy submissions.

This guide is for partner engineering teams integrating the React Native SDK, relayer, and verifier.

## What Argus Verifies

For production `app_capture`, Argus verifies that:

- The partner app requested an Argus capture session.
- The photo bytes came from the native Android Argus capture path, not from React Native or a gallery import.
- The photo, canonical manifest, metadata, camera evidence, device evidence, capture session, nonce, partner ID, use case, and app identity are bound together by deterministic hashes and commitments.
- The proof bundle was accepted by an authorized production relayer fee payer.
- The accepted commitments were registered under the production-pinned Argus Registry program ID and trusted registry configuration.
- The verifier can recompute the same commitments from the offchain proof bundle and compare them with the registry record.

Argus verifies capture provenance. It does not prove physical scene truth, item existence, seller ownership, item authenticity, item condition, legal validity, or user intent.

## Integration Flow

1. Configure the SDK with trusted production relayer and verifier roots.
2. Render the Argus camera surface where the user must provide photo evidence.
3. Receive the `ArgusProof` produced by the native capture flow.
4. Submit the proof bundle to the authorized Argus relayer for production registration.
5. Store or serve the proof bundle so the verifier can recompute it later.
6. Show Verified Capture only after verifier policy confirms a production `app_capture` record.

The UI should require retake, downgrade, rejection, or manual review when verification is pending, missing, unsupported, demo-only, or failed.

## Basic React Native Usage

```ts
import { ArgusCamera, ArgusBadge, configure } from "@argus/rn-sdk";

configure({
  partnerId: "recommerce-demo",
  relayerUrl: "https://relayer.argus.dev",
  verifierBaseUrl: "https://verify.argus.dev",
});
```

```tsx
<ArgusCamera
  partnerId="recommerce-demo"
  useCase="marketplace_listing"
  metadata={{ listingId: "argus-listing-500cm" }}
  onProofCreated={(proof) => setProof(proof)}
  onError={(error) => console.error(error)}
/>
```

```tsx
<ArgusBadge proof={proof} />
```

The partner app receives an `ArgusProof` that includes fields such as `proofId`, `manifestHash`, `imageHash`, optional `solanaTx`, `verificationUrl`, `proofLevel`, compatibility `integrityLevel`, and `deviceEvidenceSummary`.

React Native displays and submits the proof object. It does not supply the production `app_capture` photo bytes. The canonical manifest and proof ID are generated by native Android/Kotlin before React Native receives the proof.

## Production Access Boundary

The SDK package can be open-source or source-available so developers can inspect the capture flow, manifest schema, evidence commitments, and verifier behavior. Source availability is not the production trust root.

Production Verified Capture requires configured access to:

- A trusted relayer root.
- An allowlisted partner ID, use case, and app identity hash.
- An authorized production relayer fee payer.
- Sponsored gas and fee-payer binding.
- The production-pinned Argus Registry program ID and trusted registry configuration.
- A proof-bundle retrieval path that lets the verifier recompute commitments.

A forked SDK or self-hosted relayer can produce compatible-looking local or demo bundles. It cannot create a production Verified Capture badge unless the authorized production relayer and verifier policy accept the bundle under the production trust root.

## Evidence Levels

Treat `proofLevel` and `integrityLevel` as verifier policy labels, not truth scores.

| Level | Integration rule |
| --- | --- |
| **Level 1 - Demo / bundle check** | Preview-only flow. Matching local hashes, local records, or demo transaction references do not earn the production badge. |
| **Level 2 - Verified Capture (`app_capture`)** | Current production path when native Android capture evidence, byte/manifest/evidence commitments, nonce/session binding, production registry/configuration, authorized relayer fee payer, sponsored gas, and partner/use-case/app identity policy all verify. |
| **Level 3 - Keystore-signed binding** | Level 2 plus a verifier-validated Android Keystore signature over the proof manifest or binding message, with signer public key validation against partner/app policy. A bare boolean or unvalidated key must not be mapped to Level 3. |
| **Level 4 - Hardware-backed key attestation** | Level 3 plus verifier-validated Android Key Attestation certificate chain, leaf public-key binding, extension-bound session nonce challenge, TEE/StrongBox security level, and configured trusted attestation root/fingerprint. Unsupported or unverifiable attestation falls back to Level 3 or Level 2. |

Level 3 and Level 4 are app/device key evidence. They are not camera sensor signatures and do not prove that the physical scene is true.

## Proof Bundle Storage

Argus verification needs more than a photo and an onchain record. Production integrations should store or serve the offchain proof bundle keyed by `proofId`.

```text
photo bytes or platform image/evidence object key
canonicalManifestJson
metadataJson
cameraEvidenceJson
deviceIntegrityJson
proofRecord or registry reference
```

Recommended storage split:

```text
photo bytes -> platform image or evidence storage, or verifier-provided upload
manifest/evidence bundle -> partner or Argus proof-bundle store keyed by proofId
session/nonce consumed state -> relayer/backend database with short TTL
partner/use-case/app identity policy -> relayer policy configuration or database
commitments -> Argus Registry on Solana
```

The proof-bundle store is a retrieval layer, not a trust root. The verifier must recompute the photo hash, manifest hash, evidence commitments, proof ID, registry record match, production registry program ID, trusted registry configuration, authorized relayer fee payer, and sponsored gas/fee-payer binding. If the backend later serves a changed photo, manifest, or evidence bundle, verification fails against the registered commitments.

## Capture And Byte Policy

Native Android produces production photo bytes from an SDK-reserved cache capture file. Before proof generation, the SDK revalidates the expected path, name, timestamp, symlink state, file identity, and length, reads the file under the native-capture byte cap, and rejects mismatches. These checks reduce simple file-swap and TOCTOU risk; they are not an OS-level guarantee that cache bytes are immutable outside the SDK process.

For production `app_capture`, the verifier and SDK client repeat submitted-photo-byte checks:

- Canonical base64.
- 20 MiB native-capture photo byte cap.
- Basic production JPEG-like structure gate.
- SHA-256 match against `imageHash` and `manifest.image_sha256`.
- `capturedFileBytes` match against the decoded base64 byte length.
- Evidence-commitment checks.

The current RN/Kotlin/relayer path enforces these UTF-8 text caps before accepting metadata/evidence or registering a proof:

| Input | Cap |
| --- | ---: |
| Canonical manifest JSON | 4 KiB |
| Capture session ID | 4 KiB |
| Metadata JSON | 64 KiB |
| Camera evidence JSON | 64 KiB |
| Device integrity JSON | 64 KiB |

The standalone Rust core helper still caps optional evidence JSON helper inputs at 16 KiB. The Rust registry-payload builder repeats the canonical manifest JSON and capture session ID caps and rejects zero optional metadata commitments before deriving registry payload commitments.

## Verifier And Relayer URLs

`verifierBaseUrl` and `relayerUrl` are trusted integration configuration, not user-supplied routing values.

Relayer-issued verifier links use this route shape:

```text
<verifierBaseUrl>/proof/{proofId}
```

The relayer caps `verifierBaseUrl` at 2 KiB and rejects traversal after slash and backslash normalization. RN verifier API calls derive:

```text
<verifierBaseUrl>/api/proofs/{proofId}
```

The current relayer also exposes:

```text
GET /api/proofs/:proofId/photo
GET /api/registrations/:proofId/progress
```

Verifier/client proof IDs and relayer request proof/hash IDs are canonical lowercase non-zero 64-hex strings. The current RN SDK production client trusts the default production verifier origin and loopback development bases. Branded verifier bases need matching client trust support in addition to relayer allowlisting.

Loopback relayer roots, loopback verifier roots, `mock://` flows, and `argus://verify/local-simulator/{proofId}` preview links are local-development or demo-only. Production clients should submit capture bundles only to trusted relayer roots and should reject unsafe relayer roots before posting bundles.

## Demo And Preview States

Local RN, static browser preview, simulator, and mock flows may use:

- `proofLevel: "demo"`
- local demo records
- `demo_verified` results
- `relayerAuthorized: false`
- `status: "superseded"`
- simulated transaction references
- `android-native-camera-stub`

These paths are for previewing integration UX only. Partner UI must label them as demo or preview and must not display a production Verified Capture badge for them.

The production camera surface is `native_android_camera`. `android-native-camera-stub` is only for simulator or demo previews.

## Registration Boundary

Partner apps should not submit arbitrary hashes directly to Solana or treat a transaction reference as enough for a badge. They submit an Argus proof bundle to the relayer:

```text
photo bytes + canonical manifest + evidence JSON/commitments + SDK session nonce + partner app identity
```

The relayer registers only after validating:

- Capture session ID, nonce, partner ID, use case, and app identity hash form a fresh, known authorization tuple.
- Request proof/hash IDs are canonical lowercase non-zero 64-hex strings.
- Partner app identity matches configured partner policy.
- Manifest follows the current Argus schema.
- Canonical manifest, capture session ID, metadata, camera evidence, and device integrity JSON stay within configured caps.
- Proof level is supported production `app_capture` and is allowed for the partner/use case.
- Canonical `photoBytesBase64` decodes under the 20 MiB native-capture cap, passes the basic JPEG-like structure gate, and hashes to `imageHash` and `manifest.image_sha256`.
- Camera evidence uses `native_android_camera`, commits the current camera evidence summary, has `capturedAtMs` matching the manifest, has `capturedFileBytes` matching the decoded byte length, and has `captureEvidenceDelayMs` within the 5-second policy window.
- Device integrity commits the expected app identity and an accelerometer/gyroscope motion snapshot with finite 3-axis samples whose `sampledAtMs` and `sampleWindowMs` are within the 2-second capture policy window.
- Optional Level 3/4 evidence is validated before it is promoted in UI or verifier output.
- Sponsored registration fields bind `sponsoredGas` and `feePayer` to configured relayer policy.

The verifier later reapplies the same byte policy, recomputes hashes and commitments, and checks the production registry program ID, trusted registry configuration, active `ArgusProofRecord`, authorized production relayer fee payer, sponsored gas/fee-payer binding, and allowlisted partner ID/use case/app identity hash.

The verifier result is a provenance decision. The proof level helps the partner platform decide whether evidence is strong enough for its workflow policy; it is not proof of physical truth or claim validity.
